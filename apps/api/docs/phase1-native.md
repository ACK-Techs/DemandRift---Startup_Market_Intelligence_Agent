# Native Phase 1 confirmation, planning and analysis

Migration `20261002_0009` follows the immutable 001–008 chain. It adds three owner-scoped append-only tables (`plan_mutations`, `preparation_analysis_requests`, `preparation_analysis_results`) and two backend administration tables (`source_qualification_snapshots`, `source_qualification_current`). It seeds no qualifications or live permissions. Historical DTOs remain readable; new confirmed snapshots require their atomic human event receipt, and new jobs/dispatch require a current nonempty qualified plan.

`Phase1Repository(database, user_id, project_id)` inherits authenticated preparation reads and revisions. `confirm_brief(research_id, request_key, HumanBriefConfirm)` returns `(PreparationMutationReceipt, created)`; `draft_plan(..., PlanDraftCreate, compiled=ResearchPlan)`, `revise_plan(..., HumanPlanPatch, compiled=ResearchPlan)`, and `approve_plan(..., PlanApprovalCreate)` return `(PlanMutationReceipt, created)`. `compiled` is a server compiler result, never an HTTP or model authority. The repository repins the server identity, project-wide version, creation time and fingerprint under the project lock. Each graph, selected approval and receipt commits in one transaction. Exact historical request-key replay returns the original receipt before current-version or archive checks; changed input conflicts. Latest, selected historical, paged plan/analysis and scoped mutation reads are bounded.

Confirmation preserves the exact original idea bytes and separates current human fields, accepted model proposal IDs and category choice. Human-stated fields become explicitly confirmed with retained prior origins; accepting a proposal also retains its AI origin and assumption ID in the lineage. Unselected AI values remain unconfirmed. Skipping clarification requires an explicit choice to continue with unknowns. The native confirmation trigger reconstructs the selected result, and a deferred membership trigger rejects confirmed snapshots without their receipt.

`claim_analysis(research_id, request_key, PreparationAnalysisCreate, suite_id=..., prepared_fingerprint=..., reserved=ResourceAmount, metadata=..., analysis_id=None, attempt_id=None)` returns `(PreparationAnalysisOperation, created)`. The immutable claim and exact account policy commit before admission or I/O. Server-supplied IDs are stable and conflicting explicit replay IDs are rejected. A fresh preparation admission requires that committed claim, exact current brief and optional current plan, server attempt, prepared fingerprint, reservation and versioned model metadata. Only an exact already-bound historical admission replay returns a false send permit without rechecking current state. All new generic/unbound dispatch remains denied. The claim performs no provider call and does not itself grant a send.

`publish_analysis(research_id, request_key, operation, analysis=PreparationAnalysis|None, status=completed|invalid_output|overrun, output_digest=..., usage=Usage)` accepts only a known native settled/overrun attempt bound to that exact claim. Usage must match measured ledger amounts. Unknown attempts remain held and release no successful analysis; there is no timeout refund or provider replay. Completed payloads contain proposals, never human confirmation or source grants. Stored claim/result/ledger bindings and canonical payloads are revalidated on reads, with generic exceptions. Invalid output remains a measured known attempt without a released analysis. The surrounding gateway must durably spool the complete provider observation before settlement; these kernel methods contain no external I/O.

Qualification publication belongs to a backend administrator. A snapshot has a bounded `qualification_version` (48 characters), `qualification_digest = SHA256(payload::text UTF8)` computed by native PostgreSQL, review/validity/expiry dates and a one-way `revoked_at`. Its exact payload keys are `sources` (complete canonical `SourcePlanItem` templates), `registry_version`, `registry_digest` and `grant_digest`; the two digests must be nonzero 64-character hex values. The singleton current row pins `(qualification_version, qualification_digest)`. Plan `versions.source_registry` and eligibility `qualification_version` use the combined `version:digest` token. Sources must equal the current template except for limits that may narrow. The separate source loader also validates registry identity and canonical template structure. No packaged registry or historic permissions constitute publication.

The application has global metadata SELECT only, no table/column modification, trigger or grant authority. Three new owner tables use FORCE RLS and the native owner policy. Four private invoker trigger functions deny application/PUBLIC execution; the owner-scoped read-only `demandrift_phase1_plan_eligibility(uuid,uuid,uuid,uuid,integer,text)` is explicitly executable. No new SECURITY DEFINER function is introduced. Qualification readers/approval/enqueue/dispatch take a transaction advisory shared lock on fixed key `6300290009`; publication/revocation/current-pointer triggers take its exclusive counterpart. This serializes authority changes without granting SELECT-only consumers UPDATE privileges. Scope commands use FOR NO KEY UPDATE to preserve legacy FK KEY SHARE accounting lock compatibility. Lock order remains scope/job, qualification, suite, account, attempt.

Eligibility blocks stale brief/plan, unmatched or unconfirmed category, unresolved clarification or AI hypotheses, empty source/query/included-intent graphs, missing/expired/revoked/changed qualification, mismatched source authority, limits, query scope and account budget. Included intents without a query produce required native gaps with ID `coverage-` followed by the intent UUID without hyphens. Approval must select exactly the displayed unconfirmed query IDs and required gap IDs. The private compiler adjunct is not approval authority. New enqueue and dispatch recheck the current authority; historical empty confirmed plans retain their read shape but cannot execute.

Job dispatch uses the minimum plan, research-account, global-suite, lease and model timeout bounds. Plan capacity applies to existing account spent plus held amounts and the fresh reservation; plan duration uses the original account start time, so preparation spending/elapsed time does not reset at job creation. The application cannot read global suite totals. Native ledger routines remain the sole send authority. Cancellation/lease serialization applies before admission commit; an already admitted external request cannot be retrospectively unsent.

The focused tests use fresh disposable PostgreSQL databases and restricted roles. They exercise actual migrations, human event receipts, immutable known-result bindings, unknown holds, concurrent idempotency, graph rollback, raw model/confirmation forgery, qualification expiry/revocation serialization, role/column/function privileges, owner isolation and effective job budgets. They do not claim provider, HTTP service, worker or live source completion. Runtime head/guard wiring, central current-head fixture adaptation, compiler/API consumer integration and independent acceptance are separate coordinated gates.
