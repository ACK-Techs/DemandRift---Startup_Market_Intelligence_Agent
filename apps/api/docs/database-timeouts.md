# PostgreSQL bağlantı ve probe sınırları

Application bağlantıları libpq `connect_timeout=2` ve `tcp_user_timeout=2000` kullanır. Güvenilir runtime DSN tek PostgreSQL host seçer; host listesi veya tekrarlı host/hostaddr query kabul edilmez. DSN içindeki timeout override'ları bu sınırları gevşetmez. Linux TCP timeout bağlantıda karşı tarafın cevap vermediği durumları sınırlar; native macOS handshake testi Linux TCP davranışı kanıtı değildir. DNS çözümleme süresi libpq connect timeout garantisine dahil değildir; runtime Docker ağındaki tek proje PostgreSQL adıyla ayrıca doğrulanır.

`Database.readiness_probe()` application pool'u beklemeyen ayrı, fresh `NullPool` bağlantıları açar. Probe için statement timeout 500 ms ve lock timeout 250 ms'dir. Uygulamanın 10 saniyelik business statement ve 5 saniyelik lock sınırları korunur. Probe aynı DSN/rolü kullanır; admin/RLS/DDL/bütçe rol denetimini atlamaz. Her probe ve başarısız transaction kapanır; bir timeout için arka planda thread/future veya yeniden deneme oluşturulmaz.

Native kontroller sessiz gerçek libpq handshake'i, URL timeout override girişimini, application pool doluyken bağımsız bağlantıyı, server-side statement iptalini ve admin rol reddini kapsar. Worker/API readiness toplam süresi, queue bağlantısının no-retry pipeline davranışı ve gerçek Hetzner Linux ağı ayrı runtime kabul kapılarındadır.

Bağımsız incelemedeki ikinci gerçek hata, başarılı authentication sonrasında TCP paketlerini ACK eden ama sorgu sonucunu göndermeyen peer ile 16 saniyeyi aşan bloklanmadır. Server-side statement timeout bu ağ durumunu sınırlandırmaz. Yeni fresh probe, oluşturulmasından itibaren tek monotonic üç saniyelik deadline kullanır: libpq handshake, SQLAlchemy initialization, rol kontrolü, transaction, schema head sorgusu ve rollback dahil her native wait aynı kalan süreyi paylaşır. Pinned psycopg 3.3.6 `waiting.wait(..., timeout=...)` süresi dolduğunda connection doğrudan kapanır; ağ üzerinden cancellation veya bekleyen rollback, GC, arka plan thread ve retry başlatılmaz. Business connection query davranışı bu probe deadline'ını kullanmaz. DNS başlangıcına ilişkin açık sınırlılık ve gerçek Linux/container kabul kapısı korunur.

## Başarısız native bağlantı temizliği revizyonu

İlk bağımsız revizyon, bounded HTTP503 dönüşüne rağmen psycopg 3.3.6 timeout generator'ının native socket'i traceback/GC'ye kadar tuttuğunu gerçek FD/EOF gözlemiyle doğruladı; FAIL geçmişi korunur. Yeni constructor libpq `connect_start`/`connect_poll` socket'ini kendisi sahiplenir, monotonic iki saniye içinde tek attempt'i sürdürür, her başarısız path'te `PGconn.finish()` çağırır. Başarıda socket mevcut psycopg `Connection`/SQLAlchemy lifecycle'ına devredilir. Native peer EOF/RST, exception tutulurken ve `gc.collect` çağırmadan kapanmayı doğrular. DNS çözümleme libpq başlangıcında ayrı sınırlılık olarak kalır; runtime host kabulü gerekir.

Bu lifecycle, [PostgreSQL16 libpq connection control](https://www.postgresql.org/docs/16/libpq-connect.html) ve [Psycopg public libpq wrapper](https://www.psycopg.org/psycopg3/docs/api/pq.html) üzerinde tanımlanan native start/poll/finish işlemlerini kullanır. Library generator içeriği, global monkeypatch veya GC çağrısı kullanılmaz.
